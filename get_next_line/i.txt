The last KO is a real bug, and I reproduced it. It’s the same kind of thing as before, one level deeper: nextline_strjoin can fail too.

I made the malloc inside a join fail partway through a 20,000-character line with BUFFER_SIZE=10, and got this back:

call 0 -> line of 15010 chars

That’s a wrong line, not NULL. Here’s what happened:

the join fails, frees the old stash (correct) and returns NULL, so stash is now NULL
but the loop keeps going: strchr(NULL) says “no newline”, and bytes_read > 0, so it reads the next chunk...
...and starts a brand new stash from there, silently dropping everything before it

With a giant line, the tester’s NULL_CHECK has to repeat that for thousands of mallocs, and it times out.

The fix: when the join returns NULL, stop reading immediately and return NULL.

The catch: read_to_stash is at 24 lines, and another error block won’t fit. So the trick is to send all the errors through one exit instead of each one having its own free/return block. Here’s the shape with blanks:
